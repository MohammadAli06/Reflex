# Taste
- Requires scoped, verification-gated agent work: changes confined to a declared directory/layer, presentation-only (never data fetching, state, logic, or API shapes), existing test hooks and handlers preserved, proven by a scoped diff plus passing tests and build, done on a separate branch — never main. Confidence: 0.85
- Prefers documentation organized into purpose-based subfolders (e.g. problem-statement, specs, plan, reviews, presentation) rather than a flat `docs/` directory. Confidence: 0.6
- When handing over a design/UI asset (e.g. a Stitch HTML export, usually via a local file path), expects it to be implemented faithfully — same palette, typography, and layout — rather than reinterpreted or approximated from a spec. Confidence: 0.6
- Insists on no fabricated or unmeasured figures in UI/marketing surfaces; values that have no real data must degrade to a placeholder (e.g. an em dash) and read from live sources instead. Confidence: 0.8
- Likes new page styles scoped/namespaced so they don't clobber the existing app's theme (e.g. a separate scoped CSS file with its own token prefix). Confidence: 0.5
- Optimizes for speed of delivery: wants the change implemented and a build run, then stop — extra verification (dev servers, live route probing, manual browser checks) is seen as too time-consuming. Confidence: 0.75
- Prefers pnpm for running frontend scripts (e.g. `pnpm build`). Confidence: 0.5
- When supplying a concrete value (e.g. a literal CSS padding like `60px`), expects it applied verbatim rather than replaced by the agent's own approximation — substituting a different value reads as ignoring the instruction. Confidence: 0.75
- Favors minimal styling on the dark UI: dislikes decorative light chip/background treatments that clash (e.g. the global light `code` background), preferring plain, unstyled elements that "look fine" as-is. Confidence: 0.5
- Prefers complex technical topics explained in simple plain words with a complete end-to-end flow, including an ordered walkthrough for demoing/explaining multi-page UI to others and where AI/LLM fits in the architecture. Confidence: 0.6
- Prefers calm, restrained commercial UI (Linear/Stripe-like): hairline borders with spacing-and-type hierarchy instead of boxing everything, no emoji decoration, badges only for true status, sentence-case labels with no all-caps tracking, subtle purposeful motion only. Confidence: 0.85
- Demands plain, accurate UI copy with no buzzwords or unproven claims; overclaims rewritten into factual one-liners. Confidence: 0.8
- Expects visual work to start with a shared design-token plus reusable-component foundation (buttons, cards, stats, tabs, tables, steppers, code blocks, empty/skeleton states) with no per-page duplicated styling. Confidence: 0.75
- Enforces strict semantic color and typography discipline: limited hues per screen (e.g. red = failed, green = healed, amber = refusal, navy = neutral), one UI sans plus monospace strictly for code/payloads/hashes plus one serif display face for titles and big numbers, tabular numerals for metrics. Confidence: 0.75
- Requires light and dark themes equally polished with WCAG AA contrast and a working persistent toggle, plus visible keyboard focus, prefers-reduced-motion support, and skeleton plus honest empty/error states on every data view. Confidence: 0.7
- Expects a final report listing files changed, old-to-new copy changes, and verbatim verification outputs (diff, tests, build). Confidence: 0.6
- Prefers SQLite (single file, no server) via SQLAlchemy 2.0 for local/Windows hackathon backends, deferring Postgres to a future connection-string swap. Confidence: 0.85
- Keeps mock/external-service simulators in-memory and persists only the real control plane, accessed via one repository per table so domain code never touches SQL. Confidence: 0.8
- Requires SQLite correctness hardening: WAL mode + busy_timeout, batched event writes with timestamps captured before the write, hash-chained audit log with verify_chain(), and compare-and-swap via UNIQUE constraint inside a transaction. Confidence: 0.8
- Prefers safe persistence migrations: dual-write legacy files alongside DB then cut over after tests pass, and non-destructive reset (new revision / reset external mock) rather than wiping history. Confidence: 0.75
- Expects DB work proven by restart-persistence, single-byte tamper detection naming the broken entry, concurrent-CAS single-winner, and event-replay after restart, with the existing suite still green. Confidence: 0.75
- Expects code changes accompanied by docs updates, reusing the existing change-tracking markdown file in place rather than creating a new changelog unless none exists. Confidence: 0.6
- Requires secrets to never surface anywhere — logs, SSE events, audit rows, LLM prompts, UI, URLs — routing values through the existing Redactor and showing only "configured/not configured" status for keys. Confidence: 0.8
- Treats safety gates as inviolable: never weakens or bypasses a validation/refusal path to make a case or test pass; refusal must remain reachable. Confidence: 0.8
- Every new behavior must ship with automated tests, including at least one negative/adversarial case (backend pytest, frontend Vitest). Confidence: 0.8
- Preserves the entire existing test suite as a hard constraint — no regressions allowed, and verifies the actual current test counts before relying on documented numbers. Confidence: 0.75
- Prefers incremental work in small commits/steps, running the full test suite after each and reporting the real results. Confidence: 0.75
- Insists UI never be built on invented backend contracts: wire typed API calls only once the contract is confirmed, otherwise render an honest unavailable/not-yet-configured state and clearly report the missing backend dependency. Confidence: 0.75
- Verifies the actual repository source before building on it — does not assume routes, components, or endpoints described in docs or prompts already exist, and reports each spec-vs-repo discrepancy with concrete file:line evidence (e.g. "repo differs: X is what actually exists") rather than silently guessing or speculatively coding. Confidence: 0.7
- A minimal, read-only backend response enrichment (attaching already-computed fields to an existing endpoint's payload or summary, with no run/control-flow change) is considered compatible with a "do not change backend logic" constraint — but only when it's raised as an explicit decision with a recommended option and approved first. Confidence: 0.7
- Avoids adding new dependencies (UI framework, chart/icon/state libraries, animation packages) when existing ones suffice. Confidence: 0.6
- Prefers the agent to keep moving and decide scope itself rather than pausing for an explicit choice — answers clarifying/scope questions with a bare "continue" and expects the agent to proceed on its recommended defaults. Confidence: 0.6
- Expects a predictable output format for each step of work: a short plan first, then the changes, then the test results. Confidence: 0.65
- When restructuring/refactoring UI, reuse existing components, viewers, and endpoints rather than rewriting or replacing them; structural changes come via merging pages into tabs and redirects, not rebuilds. Confidence: 0.6
- Prefers to hide, not delete, when removing planned/deprecated pages: keep the code behind a feature flag (default off) and redirect old routes instead of dropping the code. Confidence: 0.55
